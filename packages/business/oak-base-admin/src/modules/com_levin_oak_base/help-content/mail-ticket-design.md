# 统一消息与邮件工单实现说明

## 1. 设计事实与边界

本实现采用“独立业务事实、统一持久投递”的模型。邮件入口确认实际收件，工单聚合负责处理状态，追加消息保留往来，通知事件保存明确接收人快照；各渠道的技术结果与个人阅读状态分别追踪。使用步骤和参数见[使用指南](?doc=mail-ticket-guide)。源码设计事实由根项目规则索引中登记的 OpenSpec 设计与规范管理；本文件描述已经存在的模块落点，不替代生产环境验收。

| 决策 | 实际约束 |
| --- | --- |
| Inbox 与 Ticket 分开 | 转单不删除邮件，不改写原 Inbox/MailBlob 归属；来源消息使用不可变关联 |
| 通知事件与业务同事务 | 原业务回滚时事件及意图同时回滚；提交后外部渠道失败单独审计 |
| 接收入口确定租户 | 验签路由或可接收 Domain 是事实源，用户邮件头不能指定租户/身份 |
| 当前队列限定受理人 | 操作权限加启用队列用户/角色资格；不存在隐式同组织全工单权限 |
| 外发先保存意图 | 固定联系人、From/To、会话、配置指纹与内容快照不可随重试改写 |
| Unknown 保守处理 | 外部调用开始后的不确定结果不自动重发，人工核验与重试分离 |
| 个人已读单独保存 | 看过消息不代表完成任务、解决工单或外部邮箱送达 |

## 2. 模块落点与模型

`entities` 定义 Inbox、私有 MailBlob、Ticket、追加式 TicketMessage、TicketQueue、SupportMailboxRule、TicketOutboundIntent、NotificationEvent、NotificationDelivery、NotificationDeliveryAttempt、UserMessage 和 NoticePublication。实体及生成默认服务/控制器的模型更新遵循先编译实体再生成的顺序；业务行为位于 `services` 的业务接口/请求与 `services-impl` 的实现，不手改生成目录。

`admin-api` 提供受控聚合入口：Inbox 私有下载/转单、TicketQueueAction、SupportMailboxRuleAction、TicketAction、UserMessage/use、NotificationAudit 和 Notice/myDetail。邮件事实、工单、工单消息、通知内部对象及私有字节不开放通用增删改入口。API 默认前缀为 `/com.levin.oak.base/V1/api/`；前端路由是另一层路径。

关键完整性边界：

1. Inbox 非空 `inboundKey` 唯一，原始 MIME 摘要与稳定重投摘要分开；实际收件地址参与身份。
2. MailBlob 保存原文、附件或内嵌资源字节及大小、类型、摘要、来源与相同归属，未提供公共文件 URL。
3. Ticket 首次 `sourceInboxId` 唯一；TicketMessage 的入站来源及外发意图分别唯一，消息只追加。
4. NotificationEvent 使用稳定作用域/来源动作键，重复同内容复用，同键异内容拒绝；Delivery 按事件、渠道和目标唯一，领取、尝试和结果分别持久化。
5. NoticePublication 固定接收用户、对应作用域及摘要，分批追加不能扩张发布时受众。
6. TicketOutboundIntent 固定稳定回复键、消息标识、受控收发身份、内容及配置摘要；外部提交不与数据库长事务绑定。

Inbox 及入站工单消息正文使用可容纳 MIME 边界的 TEXT 存储，外发正文支持请求允许的100000字符。会话引用采用不冲突的字段映射，不靠短 varchar 或数据库建表警告截断合法内容。

## 3. 入站原子性与归属

`BizInboxServiceImpl` 处理受管 Forward Email 回调和本地 SMTP DTO。Forward 先逐收件人匹配服务端路由并验签，再解析 MIME；官方结构化 From 使用唯一 `value.address`，拒绝多个发件邮箱、展示文字及头部注入。Local 重新加载实际 Domain，核对启用、收件开关、有效期、生命周期及收件域；DTO 不提供租户覆盖能力。

接收归属读取使用最多两条的 Criteria 标量投影，只获取候选标识、租户与组织，不伪造请求主体的管理员标志。明确入口只查询自身租户，唯一用户/组织保留其原归属；其余回退至入口租户。平台共享入口仍检测歧义，不选择“第一条”。

`BizInboundMailPersistenceServiceImpl` 在一个事务中保存 Inbox、RawMime、附件引用、工单受理和相关通知意图。MIME 限制在解析和字节保存前检查。非资源超限的解析错误保留原文与安全原因；超限不部分保存。本地 SMTP 仅在接受的收件人完成保存后回复250，暂时保存失败回复451；部分已提交地址重投复用。

`BizTicketIntakeServiceImpl` 锁定 Inbox，核验当前规则、来源、队列和默认负责人，再建单或追加。同租户无来源组织只能由明确规则映射受理组织，原私有文件不改归属。入站会话候选同时限定租户、组织、支持邮箱、来源/外发关联及固定参与者。外发候选仅来自已关联消息且意图为 Accepted/Unknown；待发送、发送中、确定失败不会作为已发会话候选。

认证证据来自受签名供应商快照；数据库 JSON 嵌套对象可由不同 Map 实现承载，但必须是结构化对象并完整通过对齐校验，字符串“pass”或原始头自称通过均不接受。本地 SMTP 缺少这种证据，因此不会自动追加回复或重开。

## 4. 工单状态、授权与有界读取

`BizTicketServiceImpl` 使用 TicketStatus FSM 执行分派、处理、解决、重开及关闭，强制预期版本和当前队列资格，在更新事务内增量追加 ActionLog 并记录安全事件。确定成功后以真实已写入状态响应；默认 CRUD 不能设置状态或覆盖日志。

队列资格要求当前处理资源权限、有效用户、当前租户/组织、启用队列及允许用户或角色。列表总数和分页在 Criteria SQL 内组合队列 JSONB 资格与本人参与关系，详情、操作和联系人核验重新检查。本人请求人/负责人可以按已有参与关系只读，但资格失效后不拥有处理事件。队列成员可以协作处理本队列，不要求界面额外猜测“只有负责人才能操作”。

消息列表首先核验 Ticket，再用租户/组织/工单条件查询。SQL 只选择白名单字段、有界正文前缀与完整字符数，避免一次把100条大正文加载进应用。Java 再按 UTF-8 字节将结果限制为64 KiB，不拆 Unicode 码点并返回截断标志。全文端点重新限定同工单消息标识，持久正文不变。

固定联系人确认只把现有请求人邮箱写为确认快照：受管对齐 DMARC 可以初始化，人工操作需要当前处理及独立确认权限、行锁、版本和无机密核验引用。请求不能接受替代邮箱；确认操作记录主体和时间，不改变处理状态。

## 5. 外发与私有附件

`BizTicketReplyServiceImpl` 将回复、发送意图、关联消息及流程事实原子保存。外发配置必须来自当前租户实际设置，不回退平台设置；配置 `fromEmail`、支持邮箱及固定 From 一致，认证 `username` 可以独立使用供应商 API key 用户名，To 来自当前已核验联系人。正文最多100000字符，附件最多20项且必须属于本工单关联来源邮件。

提交后调度用独立事务领取，外部发送前重新核验操作者、队列、联系人、配置指纹、附件及内容摘要。确认 SMTP 受理记 Accepted；调用开始后无法确定的错误或过期领取记 Unknown，发送前确定异常记 Failed。尝试最多5次，人工重试不清零、改写内容或生成新消息标识。Unknown 的独立人工核验权限、当前意图版本、安全引用和行锁检查将已确认未受理的记录转为 Failed，不触发发送；重试是另一动作。该入口已有单元及隔离 PostgreSQL 证据，完整目标环境 HTTP/浏览器与真实回执仍有验收边界。

工单附件授权以不可变消息关联为入口，并复核原 Inbox 租户/组织/所有者、当前引用成员、MailBlob 归属与摘要。工单阅读权限不使原文成为公共资源；RawMime 通过单独 Inbox 授权。二者下载均禁缓存、禁类型执行并强制附件。

## 6. 统一通知、个人消息和公告

工作流通知路由被转换为统一事件和精确用户渠道集合。站内/Email 使用当前事件确定的用户，机器人使用受控租户配置引用；群目标独立去重，不乘以用户人数。工作流 outbox 的 Applied 只证明可靠入队，不证明外部成功。邮件渲染固定基础 HTML 和纯文本，受控 HTTPS 基地址按 hash/history 生成真实任务/实例定位；正常登录与来源业务授权仍是必需。

渠道调度默认启用、每批50（最多100）、周期30秒，并隔离各渠道故障。Station 原子保存本人消息、尝试及成功结果；Email 和机器人领取事务先提交，再调用外部服务。发送前目标失效明确停止；外部结果无法确认保守 Unknown，不自动重复。生产方创建 Delivery 必须显式初始化 attemptCount=0，不能依赖生成请求把实体默认值保留下来。

`UserMessage/use` 只操作本人摘要、受控来源引用及阅读状态；完整来源重新授权。未读数与分页使用同一作用域，读取不写已读，批量标记整批校验且首次已读时间不改写。消息中的旧权限快照不替代来源的当前权限。

公告发布先捕获最多100000名合格候选及用户作用域，后台每批100追加站内意图。租户公告只选择同租户；平台公共公告可选择明确跨租户受众，各人投递仍保存其范围。后续撤权、下架、到期、来源变动或作用域变化会停止投放或拒绝本人详情，新加入者不能补入旧快照。通知审计与人工核验仅返回受控状态、时间、次数和日志，不暴露正文、目标或配置秘密。

## 7. 已验证事实及交付限制

本机隔离 PostgreSQL 17 已验证实际生成 CRUD 与 EntityManager 的工单入站链、真实 HMAC 校验、私有字节/消息/事件原子提交与回滚、并发一次受理及数据库唯一约束；JSON 队列资格、分页总数、消息范围、固定联系人及撤权控制也经过实际 SQL 检查。实际 James Socket 验证包含250、550、552、451、多收件人部分失败、并发重投以及超过32600字符的合法正文完整入库。消息列表 StatementInspector 证明 SQL 使用有界前缀而未直接选择全文列。

这些分层证据不等于生产全链路验收。完整 HTTP 认证过滤器、浏览器登录回跳与菜单、实际 DNS/Nginx/TCP25、真实供应商回调、第三方邮件客户端展示及最终送达仍须在目标环境核验。人工核验仍须具有真实未受理证据，不能仅凭技术超时调用重试。

应用没有执行存量共享/生产数据库迁移。新表、非空身份、唯一约束、正文类型及历史对象处置必须由显式批次交付完成，不通过启动、普通 GET、后台任务或运行时双写偷偷转换旧数据。本文件及[使用指南](?doc=mail-ticket-guide)不包含凭据、环境专用日志或运维执行记录。
