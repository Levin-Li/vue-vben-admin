# 工作流通知邮件使用指南

## 1. 用途与当前交付状态

工作流通知邮件提供基础 HTML 排版，并带有“打开办理页面”链接。接收人可在邮件客户端打开链接，进入管理端工作流页面，按当前身份与任务权限查看或办理。邮件同时提供纯文本替代正文，客户端不显示 HTML 时仍能读取摘要与链接。

固定 HTML 渲染、双正文、真实任务/实例定位及统一通知事件接入已经实现，并有分层测试。工作流交付任务仅在持久事件与渠道意图入队后标记 Applied；完整登录回跳浏览器、真实外部邮箱客户端与公网环境仍须单独验收，不能据此宣称整套生产链已完成。统一配置、审计与结果边界见[统一消息与邮件工单使用指南](?doc=mail-ticket-guide)，模块事实见[实现说明](?doc=mail-ticket-design)。

一般邮件接收、域名 DNS 与发信插件入口见[邮件收件模块功能与使用手册](?doc=mail-receiving-admin)，工作流配置与权限见[工作流平台使用指南](?doc=workflow-platform-guide)。

## 2. 配置前提与部署参数

1. 管理端须有公网用户能访问的 HTTPS 地址，证书和站点部署有效；公开地址由部署方配置，不从邮件内容、请求 Host 或用户提交的 URL 推导。
2. 配置具有权限管理的默认邮件发送插件，包括外部 SMTP 主机、端口、传输策略及认证。发信使用外部 SMTP；本地 James 入站端口不提供通知外发中继。凭据仅保存在受控配置，不放进通知正文或链接。
3. 工作流通知规则由服务端确定精确接收用户。邮件发往这些用户在事件时点确认的受控邮箱，不以路由中任意外部邮箱列表替代受众。无有效目标、停用用户或跨租户用户不能获得隐式投递。
4. 设置下列后端部署参数，并使路由模式与实际前端 `VITE_ROUTER_HISTORY` 一致。默认使用 `hash`；切换 `history` 时需要前端对应构建及代理页面回退配置。

| 参数 | 值与含义 |
| --- | --- |
| `oak.base.notification.public-app-base-url` | 必填的受控 HTTPS 站点地址，可带部署子路径，例如 `https://console.example.com` 或 `https://console.example.com/admin` |
| `oak.base.notification.public-app-router-mode` | `hash`（默认）或 `history`，其它值拒绝 |

Spring 配置示例：

```yaml
oak:
  base:
    notification:
      public-app-base-url: https://console.example.com/admin
      public-app-router-mode: hash
```

基地址不能含用户名/密码、查询参数、`#` 片段、路径穿越或编码路径。不要把工作流完整 URL 填入基地址。缺失或非法地址不能产生有效办理链接；工作流邮件渲染明确失败，不静默发送伪造入口。配置错误须在发生外部发送前处理，具体投递状态以当前实现及审计为准。

## 3. 邮件内容与链接格式

固定模板支持标题、摘要段落、任务/实例信息列表、强调文字和办理链接。所有动态标题、摘要及标识都按文字转义：输入 `<script>`、HTML 标签或恶意 URL，只显示为文字。模板不执行用户 HTML、脚本、表单或流程变量表达式；不支持从邮箱内直接提交审批。

链接由固定本地路由 `/clob/V1/MyWorkflow` 与服务端确认的真实动作目标生成。任务类提醒使用 `taskId`，流程结果等实例类提醒使用 `instanceId`；标识经过 URL 编码，只传定位信息。

| 部署模式 | 示例链接 |
| --- | --- |
| 根路径，hash | `https://console.example.com/#/clob/V1/MyWorkflow?taskId=task-123` |
| 子路径，hash | `https://console.example.com/admin/#/clob/V1/MyWorkflow?instanceId=instance-123` |
| 根路径，history | `https://console.example.com/clob/V1/MyWorkflow?taskId=task-123` |
| 子路径，history | `https://console.example.com/admin/clob/V1/MyWorkflow?instanceId=instance-123` |

`task-123` 和 `instance-123` 仅为格式示例，不能代替真实工作流标识。链接不含访问令牌、验证码、SMTP 凭据、任意回跳 URL 或自动操作指令。收件人不能通过改写 URL 获得其他用户的任务权限。

## 4. 接收人如何使用

1. 打开邮件，核对标题与摘要，点击“打开办理页面”；纯文本客户端可打开正文中的同一 HTTPS 链接。
2. 未登录时走正常登录链路；登录后应恢复原来的安全任务/实例定位目标。不要使用邮件作为登录凭据，也不要把邮件链接复制到需要输入密码的第三方站点。
3. 页面通过受控任务/实例详情 API 重新校验当前用户、租户、参与资格、业务对象范围和任务状态。活动任务只有当前有权办理者可以操作；已经结束的任务按当前历史权限只读显示，撤权或来源不可访问时不能办理。
4. 在页面检查业务信息后显式提交允许的动作。仅打开邮件、点击链接、浏览器刷新或邮件客户端预取 GET 链接，不批准、拒绝或修改业务状态。读过通知也不等于办完任务。

接入页面使用 `GET workflow-runtime/task?taskId=...` 或 `GET workflow-runtime/instance?instanceId=...` 定位目标，两接口需要正常登录并独立进行当前授权检查。不能把“曾收到通知”作为任务详情的访问权限；页面不得直接读取引擎表或绕过业务对象权限。

## 5. 投递与失败语义

工作流通知交付任务 `Applied` 表示事件与渠道意图已可靠入队，审批结果不会因之后邮件失败而回滚；外部邮件结果由逐渠道投递审计单独表达。邮件、站内及共享机器人目标独立记录结果，站内阅读状态单独保存。

邮件渠道 `Delivered` 只表示受控 SMTP 插件确认提交成功，不等于目标邮箱最终送达或用户已阅读。断连、超时等已开始外部发送但结果无法确定的情况进入 `Unknown` 待核验，不能盲目自动重发。发送前发现用户停用、目标邮箱指纹变化、非法目标或配置错误时停止投递；目标变化后不得悄悄改发新地址。管理员通过 NotificationAudit 的独立核验与重试操作保留证据及版本；未核验 Unknown 不可直接重试。具体参数见统一使用指南。

| 现象 | 核对方法 |
| --- | --- |
| 邮件没有办理链接或渲染失败 | 核对真实动作目标、公开 HTTPS 基地址及路由模式；不能人工拼入任意 URL 绕过校验 |
| 打开后落到首页或页面 404 | 核对前后端 hash/history 是否一致、部署子路径与 history 代理回退配置 |
| 登录后未恢复目标 | 保留原安全目标，检查宿主登录回跳链；本机组件测试不能替代浏览器完整验证 |
| 提示无权或任务不可办理 | 核对当前账号、租户、参与资格、权限撤销与任务是否已结束；邮件不授予新权限 |
| SMTP 提交成功但邮箱未收到 | 核对供应商受理、退信、收件地址与垃圾邮件规则，不把提交成功表述为最终送达 |
| 待核验 | 先核对供应商或受控 SMTP 回执，明确是否已受理，再决定是否发起一次审计保留的重试 |

## 6. 最小验证与证据边界

1. 在隔离测试环境创建有真实业务关联和合法接收人的任务，触发通知；检查 HTML 与纯文本正文、真实目标标识以及正确 hash/history 链接。
2. 在标题/摘要放入 HTML 标签与特殊字符，确认仅显示文字，邮件只有模板生成的受控办理链接，不含凭据。
3. 用未登录浏览器打开链接，正常登录后确认定位同一任务；分别验证 hash、history 和部署子路径。
4. 用合法当前办理者、其他租户用户、撤权用户访问同一定位目标，确认只交付当前有权内容；完成任务后重新打开邮件链接，确认不可重复办理。检查单纯 GET 和邮件预取没有修改业务状态。
5. 用实际外部 SMTP 和真实邮件客户端验证双正文显示、链接及提交结果，再根据独立可信回执区分提交与最终送达。

已有分层验证覆盖渲染转义、非法地址/模式拒绝、hash/history/子路径构造、双正文 MIME、任务定位组件与实际 Flowable 任务/历史权限检查。完整浏览器登录回跳、真实公网部署、外部邮件供应商和客户端显示仍须独立验收，不能由单元测试、构建成功或本机 Socket 通过替代。
