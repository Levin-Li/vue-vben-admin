# EditableObject 标准 CRUD 使用说明

## 适用范围

实体实现 `EditableObject` 时，公共 `CrudPage` 根据服务端记录中的 `editable` 判断可编辑性。记录明确为 `editable=false` 时，即使页面没有配置该字段，也只有超级管理员（含顶级超级管理员）可以编辑；租户管理员、平台管理员或普通管理员身份不构成例外。字段元数据仍决定可编辑开关的展示与能力声明；未声明该能力且记录未携带只读标志的页面保持原有行为。

## 页面行为

- 超级管理员在查询、新增、编辑和列表中看到“是否可编辑”，并可操作 `editable=false` 的记录。
- 非超级管理员在上述四处均不看到该字段；服务端记录明确为 `editable=false` 时，不提供内置编辑、删除和快捷布尔更新。已声明 `editable` 能力元数据却未返回 `true` 的记录同样不允许修改。
- 系统设置页的“编辑值”遵循同一超管例外；普通用户仍受记录 `editable` 标志控制。
- 自定义更新路径、编辑前详情加载、独立 JSON 编辑和行内启用开关均遵守原记录的只读边界；普通用户不能借回调或陈旧控件事件提交只读记录。
- 列表详情仍可按原有权限查看。页面展示设置不会放宽上述字段和操作权限，服务端 API 权限仍是最终边界。

## 操作授权与更新定位

标准 CRUD 从对应 API 方法的资源操作声明计算新增、详情、编辑和删除资格。`createPath`、`detailPath`、`updatePath`、`deletePath` 只决定请求地址，不作为 RBAC 资源表达式参与匹配；菜单展示通配权限不能凭这些原始 URL 获得业务操作权限。自定义 API 回调仍使用其实际方法的操作声明。

编辑表单不展示或不提交租户输入时，更新请求仍保留原记录的 `tenantId` 作为目标定位上下文。普通更新、API 更新回调、自定义更新路径、独立 JSON 编辑及行内启用操作遵循同一规则：最终载荷已有显式租户值时不覆盖；缺失时只补原记录中有效的租户，不从当前用户或全局选择器猜测。定位租户不表示变更记录归属，也不把租户加入 `forceUpdateFields`。后端仍须验证实际目标、租户、可编辑标志和操作权限；完整上下文契约见[全局选择器 Header 与授权契约](global-selector-header-contract.md)。

## 接入与最小验证

在页面配置中保留后端下发的 `editable` 字段元数据，使用标准 `CrudPage`，无需额外开关。分别以超级管理员和普通用户打开同一支持 `EditableObject` 的页面：检查四处字段显隐、即使未配置可编辑控件仍生效的 `editable=false` 行操作，以及对应更新请求的成功或权限错误。再用仅修改备注的普通与自定义更新核对载荷中的原记录租户定位值，确认 `editable`、参与方和租户归属未改变。若接口拒绝，按服务端权限和数据范围诊断；不要仅根据按钮显隐推断服务端已授权。
