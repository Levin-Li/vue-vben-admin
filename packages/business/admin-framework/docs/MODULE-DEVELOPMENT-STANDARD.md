# 模块使用与二次开发规范

本规范适用于使用本发布模块的子项目。子项目在引入、配置、扩展、升级或发布依赖本模块的功能时，必须遵循本规范。

本规范只约束模块消费方可共同遵循的开发边界；不要求采用发布方的代码包名、源码目录、业务对象、生成器、注解、构建脚本或部署环境。文中的 `<模块>`、`<扩展点>`、`<配置键>` 均为中性占位符，不对应任何特定实现。

## 1. 公开入口与依赖边界

- 子项目必须通过发布构件声明的公开运行、类型和 API 入口使用模块，不得复制模块源码、依赖未声明的内部文件，或把构件内部实现当作稳定契约。
- 子项目需要自定义行为时，必须优先使用文档化的配置、扩展点、回调、接口或覆盖机制；不得修改依赖构件内容，也不得通过反射、路径猜测或运行时覆盖私有状态实现业务功能。
- 自定义代码的命名空间和目录由子项目自行决定，但必须与模块公开类型、资源和配置键保持清晰边界，避免同名覆盖或隐式替换。

## 2. 扩展与兼容性

- 扩展实现必须只依赖已发布版本中公开且有文档说明的能力；升级模块版本前，必须核对版本说明、废弃公告和公开 API 兼容性。
- 子项目不得修改模块的既有公开行为来满足自身需求。需要不同业务语义时，应在子项目层新增适配或扩展实现，并保持模块默认行为可用。
- 对外暴露的扩展接口、配置项和数据结构必须说明兼容策略；移除、改名或改变语义时，应提供迁移说明或兼容期。

## 3. 配置、安全与数据处理

- 配置必须通过模块公开的配置入口提供。密钥、令牌、证书和个人敏感数据不得写入源码、发布包、示例、日志、异常信息或前端可见配置。
- 高风险功能必须由服务端执行身份、权限和数据范围校验；前端展示、隐藏或禁用只可改善体验，不能作为安全控制。
- 在线调试、预览或试运行不得把可执行代码正文作为未经验证的请求参数；应引用已保存且已授权的配置，并限制运行参数与上下文数据。

## 4. 验证与升级

- 子项目接入或升级模块后，必须至少验证公开入口可解析、核心业务链路可运行、关键配置生效、权限边界未被绕过，以及异常场景能正确失败。
- 子项目的测试不得依赖模块内部目录、未公开类型或偶然的实现细节；测试应覆盖实际使用的公开 API、扩展点和配置行为。
- 发布依赖本模块的版本前，必须确认锁定的模块版本、构建产物和运行时依赖一致；不得用本地链接、覆盖配置或未发布源码掩盖版本兼容问题。

## 5. 问题反馈与示例

- 发现模块缺少公开扩展能力时，应说明所需业务能力、使用的模块版本、最小复现和预期行为，不应直接复制或修改模块内部实现。
- 任何包含具体代码包名、目录、类名或配置名称的内容仅能作为非规范性示例，并必须明确其不构成对子项目的强制要求。

> 非规范性示例：子项目可以在自身命名空间下实现 `<模块>` 提供的 `<扩展点>`，并通过公开配置注册。示例中的名称仅用于说明结构，子项目可按自身架构命名。
