# Levin 后台基础组件项目第三方用户手册

本文面向使用本项目 npm 私服包的第三方团队。当前项目定位是后台基础组件和模块化前端工作区，不是单一业务系统源码，也不是以源码目录拷贝的方式交付给最终项目。框架包和基础模块包都按“公共模块”维护：公共模块提供稳定运行时、默认页面、默认路由映射和可复用组件；最终业务应用只装配这些模块，并在确有项目差异时通过同规范路径覆盖某个页面实现。第三方项目应通过 npm 包安装、装配和覆盖来使用本项目能力，避免长期复制框架或基础模块源码。npm 包的正式编译和运行入口是构建后的 `dist`；随包携带的 `src` 和文档只是发布物内的参考资料，用于源码查看、调试和问题定位，不作为第三方应用的公共编译入口，也不应通过 `@levin/*/src/...` 深路径参与正式应用编译。

## 1. 项目定位

本项目提供后台系统的基础组件、公共运行时、模块化装配能力和基础业务模块。推荐集成形态：

```text
最终后台应用
  = @levin/admin-framework
  + @levin/oak-base-admin
  + 一个或多个第三方业务模块包
  + 薄宿主应用 bootstrap-app
```

核心原则：

- 公共能力从 npm 私服安装，不复制源码。
- 第三方应用通过包根入口或文档声明的子路径使用 `dist` 构建结果，不直接从 `@levin/*/src/...` 引入源码。
- 最终应用只负责启动、后端地址、主题、偏好、启用模块和页面覆盖。
- 业务页面和 API 放在各自模块包中独立发布。
- 公共模块可以提供具体功能页面的默认实现，但该页面必须能被最终应用用同一页面注册路径覆盖；覆盖只替换前端组件实现，不改变后端菜单 `path`、权限点和页面注册语义。
- 菜单、权限和页面可见性以后端当前用户授权结果为准。

## 2. 包分层

### 2.1 公共框架包

`@levin/admin-framework` 是基础组件项目的核心入口，提供：

- 应用启动和挂载能力。
- 登录、布局、路由守卫、菜单同步和 RBAC 权限判断。
- 通用 CRUD 页面、表格、表单、弹窗、上传、JSON/代码编辑、权限组件。
- 页面注册、页面覆盖、模块注册、国际化合并。
- 请求适配、API service 基类、事件总线、顶部栏扩展区、窗口级可拖拽悬浮面板。

第三方项目优先从稳定入口导入：

```ts
import { configureAdminApplication } from '@levin/admin-framework';
import { bootstrap } from '@levin/admin-framework/framework-commons/app/bootstrap';
```

### 2.2 基础业务模块包

`@levin/oak-base-admin` 提供 `com.levin.oak.base` 基础模块，包含用户、角色、权限、菜单、组织、租户、通知、文件资源、系统设置等后台基础页面和 API。

基础模块默认后端 API 前缀：

```text
/com.levin.oak.base/V1/api
```

### 2.3 Vben 基础组件包

项目同时发布一组 `@vben` 和 `@vben-core` 基础能力包，例如：

- `@vben/common-ui`：常用 UI 容器和业务 UI。
- `@vben/layouts`：后台布局、菜单、页签。
- `@vben/request`：请求能力。
- `@vben/preferences`：偏好设置。
- `@vben/stores`：通用状态。
- `@vben/icons`：图标能力。
- `@vben-core/form-ui`、`@vben-core/menu-ui`、`@vben-core/tabs-ui`、`@vben-core/popup-ui`：更底层的 UI 能力。

普通第三方应用通常不需要直接安装所有包，只需安装 `@levin/admin-framework`、业务模块包和 peerDependencies 要求的运行时依赖。

### 2.4 常用公共能力速查

第三方项目优先使用下列公共入口，不要复制框架源码或从包内 `src` 深路径引入：

### 2.5 公共 API service 清单

框架公共 API service 统一从 `@levin/admin-framework/framework-commons/app/api` 导出。第三方模块需要上传、权限、登录、枚举、缓存、JsonSchema 或插件管理等公共能力时，应优先使用这些 service，不要在页面组件里直接拼接公共接口地址。

可以按聚合入口导入：

```ts
import {
  fileStorageService,
  rbacService,
} from '@levin/admin-framework/framework-commons/app/api';
```

```ts
import { fileStorageService } from '@levin/admin-framework/framework-commons/app/api/file-storage-service';
```

## 3. 安装

推荐使用 pnpm：

```bash
pnpm add @levin/admin-framework@<version> @levin/oak-base-admin@<version>
```

具体版本以私服中已发布版本和业务模块 `peerDependencies` 为准。升级公共框架包时，应同步升级依赖它的业务模块包版本约束，避免最终应用安装到不匹配的框架和业务模块组合。

运行环境要求：

- Node.js `>=20.19.0`
- pnpm `>=10.0.0`
- Vue `>=3.5.0`
- Vue Router `>=4.0.0`
- Pinia `>=3.0.0`
- Ant Design Vue `>=4.0.0`

依赖应从 npm 私服安装。测试、生产和交付环境不要使用复制源码的方式集成公共框架或基础模块，也不要从 `@levin/admin-framework/src/...` 或 `@levin/*-admin/src/...` 深路径导入源码。

发布包内可能包含 `src` 目录和文档，它们是第三方开发过程中的辅助资料：用于阅读实现、排查问题、提交问题定位信息或本地临时联调。正式应用编译应以 `package.json` 的 `main`、`module`、`types` 和 `exports.default` 中声明的 `dist` 入口为准；`exports.development` 只用于本仓或源码联调时保持根入口和子路径入口读取同一份源码实例。

## 4. 薄宿主应用接入

第三方最终应用应保持“薄宿主”结构，只做装配：

```text
src/
  main.ts
  modules/list.ts
  pages/                # 页面覆盖层
  preferences.ts
```

### 4.1 声明启用模块

```ts
import type { AdminFrontendModule } from '@levin/admin-framework';

import { createOakBaseAdminModule } from '@levin/oak-base-admin';

export const enabledFrontendModules: AdminFrontendModule[] = [
  createOakBaseAdminModule(),
];
```

第三方业务模块也应导出类似的模块工厂函数，然后加入 `enabledFrontendModules`。

### 4.2 配置应用服务

```ts
import {
  configureAdminApplication,
  defineAdminPageOverrides,
  type AdminPageMap,
} from '@levin/admin-framework';
import {
  menuService,
  noticeService,
  userService,
} from '@levin/oak-base-admin/modules/com_levin_oak_base/api/index';

import { enabledFrontendModules } from './modules/list';

const pageOverrides = defineAdminPageOverrides(
  import.meta.glob('./pages/**/*.vue') as AdminPageMap,
);

configureAdminApplication({
  menuSyncService: menuService,
  modules: enabledFrontendModules,
  noticeService,
  pageOverrides,
  userSecurityService: userService,
});
```

### 4.3 启动应用

```ts
const { bootstrap } =
  await import('@levin/admin-framework/framework-commons/app/bootstrap');

await bootstrap(namespace);
```

`namespace` 建议由项目标识、版本和环境组成，用于隔离偏好设置和本地存储。

## 5. 页面、菜单和权限

模块提供页面注册表和后端菜单路径映射。真实菜单应以后端当前用户授权菜单为准，前端根据菜单路径匹配模块注册页面。

超级管理员执行“上传页面路由”时，必须上传最终应用中所有已启用前端模块的页面路由，不得只上传当前模块、默认模块或基础模块。每个业务模块应维护自己的 `backendRouteMappings`，并在每条页面映射中提供：

- `path`：后端菜单或控制器路由路径，也是上传 payload 中的菜单入口字段。
- `viewPath`：前端运行时页面注册路径，例如 `/system/com_levin_oak_base/user/index.vue`。
- `sourceFilePath`：相对于前端源码目录的页面文件路径，例如 `modules/com_levin_oak_base/views/user/index.vue`。

这几个字段的职责不要混用：`path` 是后端菜单入口；`viewPath` 是运行时真正用于加载页面组件的注册路径；`sourceFilePath` 仅用于展示、排查和源码定位。历史文档中出现过的 `sourcePath`、`targetPath`、`view` 和 `sourceFile` 已废弃，第三方模块不要再使用。

这样拆分的目的是把“后端菜单入口”“前端运行时页面”和“源码调试位置”解耦：后端只关心菜单和权限挂在哪个 `path` 下；前端运行时只根据 `viewPath` 找到已经注册的页面组件；调试和生成工具再通过 `sourceFilePath` 追溯页面来源。第三方模块接入时不需要猜测页面来自哪个包，也不需要把源码路径当作运行时路径使用，模块覆盖和最终应用自定义页面也能保持稳定。

`moduleId` 不作为后端接口必填项；但前端模块存在自己的模块 ID 时，上传时每个菜单项都必须带上该菜单所属模块的模块 ID。

前端页面路由中的模块 ID 不能由前端自定义，必须使用后端 Java 根 POM 约定的模块包名，例如 `com.levin.oak.base`。如果上传代码取 `AdminFrontendModule.name` 作为 `moduleId`，则该模块对象的 `name` 必须等于这个后端模块包名；不要使用 npm 包名、前端页面目录名、短包名、显示名称或其它临时标识。

模块相关命名要按用途拆开：

| 名称 | 来源和用途 |
| --- | --- |
| 模块 ID / 模块包名 | 使用后端 Java 根 POM 约定的模块包名，例如 `com.levin.oak.base`，用于 `moduleId`、后端插件包名和权限归属。 |
| 前端目录名 | 由模块包名派生，把 `.` 替换为 `_`，例如 `com_levin_oak_base`，只用于前端源码目录、页面注册路径和源码定位。 |
| 短包名 | 由后端 `DefaultRbacInitServiceImpl#getShortName` 生成，取模块包名每段首字母，例如 `com.levin.oak.base` 生成 `clob`，只用于后端初始化菜单路径。 |
| 展示名称 | 用于菜单、模块选择、上传页面路由弹窗等用户可见位置；如果后端 Java 根 POM 配置了中文名称，应优先使用该中文名称展示。没有中文名称时，才使用后端插件名称、模块标题或其它稳定兜底文案。 |

上传页面路由弹窗默认全选全部本地页面路由，允许在上传前按树节点取消或重新选择。选择状态按树形菜单语义处理：选择父节点会同步选择其全部子节点；取消父节点会同步取消其全部子节点；只选择部分叶子节点时，上级节点显示为半选状态，上传时只提交已选择的节点及维持层级所需的父节点。

默认全选的目的是保证常规发布时同步完整菜单，避免第三方模块新增页面后遗漏上传；按树选择的目的则是给调试、灰度和清理历史菜单留出人工控制空间。即使只选择叶子节点，上传 payload 也会保留必要父节点层级，确保后端菜单树结构完整，但不会把未选择的兄弟节点误同步上去。

页面覆盖的本质是“同一个路由指向本地文件”：后端菜单 `path`、前端页面注册路径 `viewPath`、访问 URL 和权限入口都保持不变，只把该路由最终加载的 Vue 组件从公共模块默认文件替换成最终应用本地文件。实现上不建议让第三方重复注册一个同名同路径的 Vue Router record 去抢路由；框架和业务模块继续负责注册路由、菜单映射和权限，最终应用只通过 `pageOverrides` 注入“页面注册路径 -> 本地覆盖组件”的映射。路由访问某个 `viewPath` 时，`resolveAdminPage` 会按下列优先级选择组件：

```text
最终应用 pageOverrides 覆盖层（默认约定为 src/pages）
  > 最终应用内置页面
  > 已启用业务模块 pageMap
  > admin-framework 公共 pageMap
```

因此，覆盖已有页面时通常不需要改 router；它还是同一条路由，只是指向的页面文件换成本地文件。只有新增全新访问 URL、改变菜单结构、改变权限入口或新增业务模块路由时，才应维护模块 `routes`、`backendRouteMappings` 或后端菜单。

页面覆盖是公共框架的一等扩展能力，入口和多语言入口保持同一风格：最终应用在启动配置中统一声明一次 `defineAdminPageOverrides(...)` 或显式 `pageOverrides` 映射。`src/pages` 只是推荐默认目录，不是框架唯一识别目录；真正稳定的是“同一个页面注册路径 `viewPath` 映射到新的本地组件”。

默认用法：覆盖文件放在主应用 `src/pages` 下，文件路径自动转换成页面注册路径。`src/pages/_core/authentication/login.vue` 会规范化成 `/_core/authentication/login.vue`。

```ts
import {
  configureAdminApplication,
  defineAdminPageOverrides,
  type AdminPageMap,
} from '@levin/admin-framework';

const pageOverrides = defineAdminPageOverrides(
  import.meta.glob('./pages/**/*.vue') as AdminPageMap,
);

configureAdminApplication({
  modules: enabledFrontendModules,
  pageOverrides,
});
```

自定义用法：覆盖文件放在其它有统一根目录的地方，传入 glob 和对应根目录前缀。

```ts
const pageOverrides = defineAdminPageOverrides(
  import.meta.glob('./features/**/*.vue') as AdminPageMap,
  './features',
);

configureAdminApplication({
  modules: enabledFrontendModules,
  pageOverrides,
});
```

自定义方案 2：覆盖文件路径和 `viewPath` 没有简单前缀关系时，手写映射，显式把同一个页面注册路径指向任意本地文件。

```ts
const pageOverrides: AdminPageMap = {
  '/_core/authentication/login.vue': () =>
    import('./project-auth/custom-login.vue'),
  '/system/com_levin_oak_base/role/index.vue': () =>
    import('./features/rbac/pages/role-page.vue'),
};

configureAdminApplication({
  modules: enabledFrontendModules,
  pageOverrides,
});
```

以上三种方式可以合并使用，后声明的同一路径映射会覆盖先声明的映射。

常见 `src/pages` 约定位置：

| 场景 | 原页面注册路径 | 最终应用覆盖文件 |
| --- | --- | --- |
| 登录页 | `/_core/authentication/login.vue` | `src/pages/_core/authentication/login.vue` |
| 短信验证码登录页 | `/_core/authentication/code-login.vue` | `src/pages/_core/authentication/code-login.vue` |
| 二维码登录页 | `/_core/authentication/qrcode-login.vue` | `src/pages/_core/authentication/qrcode-login.vue` |
| 忘记密码页 | `/_core/authentication/forget-password.vue` | `src/pages/_core/authentication/forget-password.vue` |
| 注册页 | `/_core/authentication/register.vue` | `src/pages/_core/authentication/register.vue` |
| 首页 | `/_core/home/index.vue` | `src/pages/_core/home/index.vue` |
| 个人中心 | `/_core/profile/index.vue` | `src/pages/_core/profile/index.vue` |
| 404 页面 | `/_core/fallback/not-found.vue` | `src/pages/_core/fallback/not-found.vue` |
| 基础模块角色管理 | `/system/com_levin_oak_base/role/index.vue` | `src/pages/system/com_levin_oak_base/role/index.vue` |

覆盖角色管理页面示例。这里的包内源码路径只用于说明默认页面来源，不是第三方应用的 import 路径：


覆盖文件只放项目差异化内容，不要复制整个业务模块目录。

公共模块提供的默认功能页面和宿主项目覆盖页共享同一个页面注册路径。后端菜单仍指向原来的 `path`，`backendRouteMappings.viewPath` 也保持不变；运行时只是在解析 `viewPath` 时优先命中最终应用 `pageOverrides` 中的覆盖映射；默认约定下该映射通常来自 `src/pages` 下的同路径覆盖文件。因此第三方项目可以自定义某个页面的前端实现，同时保持菜单地址、权限配置、后端同步数据和用户访问入口稳定。

权限按钮、菜单可见性、数据权限等应以后端返回和框架 RBAC 判断为准。前端不要硬编码角色名、用户名或权限码来推断管理员身份。

## 6. 基础组件和公共能力

### 6.1 通用 CRUD

框架提供通用 CRUD 页面能力，模块页面通过显式配置接入，支持：

- 查询、分页、排序、刷新。
- 新增、编辑、详情、删除、批量删除。
- 表格列设置、全屏、导出。
- 权限控制和按钮显隐。
- 多类型表单组件，包括选择、树选择、上传、JSON、代码编辑、开关、日期时间、标签输入等。

查询表单默认使用响应式等宽列网格。列数按查询面板自身容器宽度计算，而不是按整个浏览器视口计算；默认每列最小可用宽度约为 `280px`，列数最少 1 列、最多 7 列。字段和操作按钮参与同一套网格布局：查询、重置、更多/收起按钮位于操作区内并靠右；当前行没有可用列时，操作区自然换到下一行。简单模式收起时，`searchCollapsedCount` 只是基础展示数量，框架会继续追加后续查询项，尽量填满操作区所在行前面的完整空列；因此无论操作区在第一行还是换到下一行，它前面的可用列都会优先展示查询项。高级查询展开后仍按同一规则排布。第三方页面通常只需要声明查询字段，不需要为按钮区单独写布局。

如果页面有特殊筛选器、跨列字段、顶部全局筛选条或其它明确交互需求，应通过页面配置显式表达，不要按字段名、菜单路径或页面路径硬编码特判。

### 6.2 事件总线

跨模块通知使用 `@levin/admin-framework` 导出的事件总线。API 请求事件统一使用：

```text
type: api.request
topic: 本次请求地址
data: 完整请求结果包
```

事件总线不替代 API service、Pinia、路由或组件 props。

需要向顶部栏中心或右侧注册控件时使用：

```ts
import { useLayoutHeaderExtensionArea } from '@levin/admin-framework';

const topRight = useLayoutHeaderExtensionArea('right');
topRight.add({
  id: 'project-current-context',

```

需要跨页面内容区浮动的上下文切换器、筛选条或工具面板时使用：

### 6.5 用户下拉菜单扩展区

需要在用户头像下拉菜单中添加第三方动作按钮时使用：

```ts
import { useUserDropdownMenuItems } from '@levin/admin-framework';

const userDropdownMenus = useUserDropdownMenuItems();
userDropdownMenus.add({
  id: 'project-help',
  icon: 'lucide:circle-help',
  order: 500,
  text: '项目帮助',
  handler: () => {
    window.open('/project/help', '_blank');
  },
});
```

第三方按钮只会出现在公共模块固定动作和 `锁定屏幕` 之间。`个人中心`、`上传页面路由`、`上传界面设置`、`监听器管理`、`锁定屏幕`、`退出登录` 都是公共固定区域，第三方模块不能替换或删除。

需要主动移除时使用注册项 `id`：

```ts
import { removeUserDropdownMenuItem } from '@levin/admin-framework';

removeUserDropdownMenuItem('project-help');
```

`useUserDropdownMenuItems().add(...)` 注册的菜单会在当前组件卸载时自动移除；入口应用注册的常驻菜单应保存清理函数，或在不再需要时调用 `removeUserDropdownMenuItem(id)`。

### 6.6 文件和图片上传

文件和图片上传统一通过基础模块后端 `FileStorageController`，前端公共封装在：

```ts
import {
  FILE_STORAGE_MULTI_UPLOAD_PATH,
  FILE_STORAGE_SINGLE_UPLOAD_PATH,
  fileStorageService,
  uploadFileByFileStorageController,
} from '@levin/admin-framework/framework-commons/app/api/file-storage-service';
```

常用场景：

```ts
const url = await uploadFileByFileStorageController(file);
```

如果当前业务模块需要带自己的 API 模块前缀，可传入 `moduleBase`：

```ts
const url = await uploadFileByFileStorageController(
  file,
  '/com.levin.oak.base/V1/api',
);
```

后端单文件上传接口返回 `ApiResp.ok(url)`，前端公共封装会把结果归一化为字符串 URL；如果接口没有返回可用 URL，会抛出“上传接口未返回文件地址”。多文件上传可使用 `fileStorageService.uploadFiles(file)` 或 `FILE_STORAGE_MULTI_UPLOAD_PATH` 配合业务上传组件。

上传成功后，页面应立即把返回的 URL 写回表单字段，并同步上传组件的 fileList。图片或附件回显依赖后端资源路径代理，宿主应用必须正确转发 `/lfs` 等资源路径。

### 6.7 用户和组织选择器

`UserOrgSelector` 用于统一处理“选用户 / 选组织 / 用户和组织都可选”的树形选择场景。组织默认在组件初始化时一次性通过 `rbacService.fetchAuthorizedOrgTree()` 拉取授权组织列表，接口语义为 `/rbac/authorizedOrgList`；也可以配置为动态加载组织子节点。用户不会随组织树一起预加载，只会在用户展开某个组织节点时动态加载该组织下的用户。

完整的公开参数、双向绑定、事件、组织类型过滤、层级压缩、懒加载边界和接入示例见包根发布文档：[UserOrgSelector 用户与组织选择器](../../../docs/components/user-org-selector.md)。该文档随 npm tarball 分发，第三方项目可直接在安装包的 `docs/components/` 目录中阅读。

本地验证入口是 `/demos/public-components`，页面内包含用户与组织选择、资源权限分配、数据权限分配三个公共组件测试区。这个页面属于 `@levin/admin-framework` demos 路由，不加入业务模块 `backendRouteMappings`，不会被“上传页面路由”同步为后端菜单。

`ResourcePermissionTreeEditor` 支持后端返回的纯树形资源权限节点。节点类型由枚举值驱动，当前内置 `Menu`、`Group`、`Action`、`Permission`、`Module`、`Resource`、`ResourceType`。展示名称优先使用 `label`，其次使用 `name`；`remark` 只作为备注数据，不参与节点标题展示。节点可以没有 `permissionExpr`，这类节点只作为组织结构；最终选中和保存都以有权限表达式的节点为准。`Action` 和 `Permission` 类型按权限项横向展示，即使后端误带子节点，也不会继续展开其子节点。

默认用户列表请求使用 `/User/list`，并且每次请求都会带上当前组织 ID：

```ts
{
  orgId: 当前组织ID,
  inType: userTypes,
  loadOrg: true,
  pageIndex: 1,
  pageSize: 500,
}
```

基础模块项目通常只需要指定用户接口所在模块前缀：

```vue
<script setup lang="ts">
import { ref } from 'vue';

import {
  UserOrgSelector,
  type UserOrgSelectorRecord,
} from '@levin/admin-framework';

const selectedId = ref('');
const selectedRecords = ref<UserOrgSelectorRecord[]>([]);
const oakBaseApiModule = '/com.levin.oak.base/V1/api';
</script>

<template>
  <UserOrgSelector
    v-model="selectedId"
    v-model:selected-records="selectedRecords"
    :org-types="['Department']"
    :user-types="['Internal']"
    mode="both"
    :user-api-module-base="oakBaseApiModule"
    @change="(record) => console.log(record?.id, record?.name)"
  />
</template>
```

常用属性：

| 属性 | 说明 |
| --- | --- |
| `mode` | 选择策略。`user` 只允许选用户，`org` 只允许选组织，`both` 用户和组织都可选，默认 `both`。 |
| `allowSelectOrg` | 是否允许选择组织。默认 `true`，仍会与 `mode`、组织类型、叶子规则共同判断。 |
| `allowSelectUser` | 是否允许选择用户。默认 `true`，仍会与 `mode`、组织类型、用户类型共同判断。 |
| `orgTypes` | 可选择、可加载用户的组织类型白名单。为空表示不限制组织类型。 |
| `userTypes` | 用户类型白名单。用户列表请求会传 `inType`，前端也会二次过滤；不匹配的用户不会展示。 |
| `onlyShowTypeMatchNode` | 是否只展示组织类型匹配节点。默认 `false`，即不匹配组织仍保留树形路径但不可选择、不可加载用户；设为 `true` 时只保留匹配节点。 |
| `onlyLeafNode` | 是否只有叶子组织可选。只影响组织可选性，不影响树形展示。 |
| `onlyNotLeafNode` | 是否只有非叶子组织可选。不要与 `onlyLeafNode` 同时设为 `true`。 |
| `maxLoadDeep` | 组织最大加载层级，`0` 表示无限制。root 节点按第 1 层计算。 |
| `rootOrgIdList` | 指定一个或多个组织作为根节点。为空使用默认授权组织根。旧参数 `orgRootIds` 继续兼容。 |
| `orgLoadMode` | 组织加载模式。`all` 一次性加载，`lazy` 展开节点时动态加载子组织，默认 `all`。 |
| `maxSelectCount` | 最大选择数量。`0` 不限制，`1` 自动单选并替换旧值，`n > 1` 超过时提示“最多只能选择 n 项”。 |
| `multiple` | 是否多选。多选时启用树形勾选；当 `maxSelectCount=1` 时会自动按单选处理。 |
| `valueMode` | `id` 表示 `v-model` 只保存 ID；`record` 表示 `v-model` 保存 `{ id, name, kind }` 结构。默认 `id`。 |
| `selectedRecords` | 用于回显和接收选中对象。组件会通过 `update:selectedRecords` 输出选中项的 ID、名称、类型和原始数据。 |
| `resolveRecords` | 当 `v-model` 只有 ID 且组件尚未加载到对应节点时，可传入该函数按 ID 解析回显名称。 |
| `orgLoadApi` | 自定义组织加载函数。为空使用默认授权组织接口；旧参数 `loadOrgTree` 继续兼容。 |
| `userLoadApi` | 自定义用户加载函数。入参固定包含 `{ orgId, org, userTypes }`，调用方必须把 `orgId` 传给后端列表接口；旧参数 `loadUsers` 继续兼容。 |
| `userApiModuleBase` | 默认用户列表加载器使用的模块 API 前缀，例如基础模块 `/com.levin.oak.base/V1/api`。 |

`orgLoadApi` 的上下文包含当前选择和加载规则，动态加载时还会包含当前父组织:

```ts
{
  allowSelectOrg,
  allowSelectUser,
  depth,
  maxLoadDeep,
  mode,
  onlyLeafNode,
  onlyNotLeafNode,
  onlyShowTypeMatchNode,
  orgLoadMode,
  orgTypes,
  parentOrg,
  parentOrgId,
  rootOrgIdList,
}
```

动态组织加载时，组件不要求后端提前返回子节点数量。未尝试加载过的组织节点会先显示展开入口，用户展开后组件调用 `orgLoadApi` 或默认授权组织接口；节点尝试加载完成后，再根据本次实际返回的组织子节点决定是否继续保留展开入口。这样不会把“尚未加载子节点”的组织误判为叶子节点。

如果业务需要自定义用户接口，可以覆盖 `loadUsers`：

```ts
const loadUsers = async ({ orgId, userTypes }) => {
  const data = await userService.list({
    enable: true,
    inType: userTypes.length > 0 ? userTypes : undefined,
    loadOrg: true,
    orgId,
    pageIndex: 1,
    pageSize: 500,
  });

  return data?.items || data?.records || data?.list || data || [];
};
```

回显示例：

```ts
const selectedId = ref('u-1001');
const selectedRecords = ref<UserOrgSelectorRecord[]>([
  {
    id: 'u-1001',
    kind: 'user',
    name: '张三',
    orgId: 'dept-1',
    orgName: '研发部',
  },
]);
```

如果不能提前拿到名称，则提供 `resolveRecords(ids)`，组件会把解析到的记录放入“当前选择”分组用于回显。

公共组件测试页或离线文档示例可以同时覆盖组织树和用户列表：

```ts
const loadOrgTree = async () => [
  {
    id: 'dept-1',
    name: '研发部',
    children: [{ id: 'dept-2', name: '平台组' }],
  },
];

const loadUsers = async ({ orgId }) => {
  return orgId === 'dept-1'
    ? [{ id: 'u-1001', name: '张三', orgId, orgName: '研发部' }]
    : [];
};
```

## 8. 后端代理要求

开发代理和生产 Nginx 至少应覆盖：

- `/com.levin.oak.base`：基础模块 API。
- 第三方业务模块自己的后端模块前缀。
- `/lfs`：文件、图片和附件资源。
- `/admin`：后端管理或直出页面。
- `/api-docs`、`/swagger`：接口文档。
- `/.well-known/acme-challenge`：证书校验路径。

前端未命中的页面路由应先回退给后端处理；只有前端和后端都无法处理时才返回 404。

## 9. 第三方业务模块开发约定

业务模块包建议结构：

```text
packages/business/order-admin/
  src/
    modules/
      com_project_order/
        index.ts
        module.ts
        routes.ts
        page-map.ts
        backend-route-mappings.ts
        api-module.ts
        api/
        views/
        locales/
          zh-CN.json
          en-US.json
  package.json
```

模块必须导出模块工厂函数：

```ts
import type { AdminFrontendModule } from '@levin/admin-framework';
import { defineAdminModuleLocales } from '@levin/admin-framework';

const locales = defineAdminModuleLocales(
  import.meta.glob('./locales/**/*.json', { eager: true }),
);

export function createOrderAdminModule(): AdminFrontendModule {
  return {
    apiModuleBase: '/com.project.order/V1/api',
    backendRouteMappings,
    locales,
    name: 'com.project.order',
    pageMap,
    routes,
    title: '订单模块',
    version: '1.0.0',
  };
}
```

模块包应把 Vue、Router、Pinia、UI 运行时和 `@levin/admin-framework` 放到 `peerDependencies`，避免最终应用出现多份运行时。

模块国际化资源必须通过模块对象的 `locales` 字段暴露。国际化覆盖是公共框架的一等扩展能力，第三方模块和最终应用都应通过 `@levin/admin-framework` 的 `defineAdminModuleLocales` 聚合语言包。`./locales/**/*.json` 是推荐默认约定，不是唯一允许目录；真正稳定的是 JSON 文件路径中能解析出规范 locale code，例如 `zh-CN`、`en-US`。

默认用法：语言包放在模块 `locales/` 目录下。

```ts
import { defineAdminModuleLocales } from '@levin/admin-framework';

export const locales = defineAdminModuleLocales(
  import.meta.glob('./locales/**/*.json', { eager: true }),
);
```

```text
locales/zh-CN.json
locales/en-US.json
locales/zh-CN/common.json
locales/en-US/common.json
```

自定义用法：语言包放在其它目录，但仍通过同一个入口聚合。

```ts
export const locales = defineAdminModuleLocales(
  import.meta.glob('./i18n/**/*.json', { eager: true }),
);
```

```text
i18n/zh-CN.json
i18n/en-US.json
i18n/zh-CN/common.json
i18n/en-US/common.json
```

自定义方案 2：不直接使用 `import.meta.glob('./locales/**/*.json')`，而是由模块自己组装记录对象，适合语言包来源需要按构建条件、模块分组或远端生成结果汇总的场景。

```ts
import zhCNCommon from './translations/zh-CN/common.json';
import enUSCommon from './translations/en-US/common.json';

export const locales = defineAdminModuleLocales({
  './translations/zh-CN/common.json': zhCNCommon,
  './translations/en-US/common.json': enUSCommon,
});
```

语言包文件必须使用规范 locale，例如 `zh-CN.json`、`en-US.json`、`zh-CN/common.json`、`en-US/common.json`。不要在模块内额外提供 `zh`、`en` 这类短语言包；公共 `@vben/locales` 会先把用户偏好或浏览器输入解析到同语系可用 locale，再合并已启用模块的语言包。

覆盖翻译时只写需要调整的 key。框架会对公共包、主应用语言包和已启用模块语言包做深合并覆盖；未声明的同级或子级 key 继续使用原有默认翻译，不需要复制整份语言包。

## 10. 发布和升级

本项目使用 npm 私服发版。发布时必须显式使用可写 hosted registry 和认证，不要把 token 写进仓库。发布物的正式默认入口必须是 `dist` 构建结果；`src` 可以随包携带为辅助资料，也可以作为 `exports.development` 条件入口用于本地源码联调，但第三方生产、测试和交付构建不得依赖 `src` 条件。

```bash
NPM_REGISTRY=http://nexus.v-ma.com/repository/npm/ \
NPM_AUTH_FROM_MAVEN=true \
MAVEN_SERVER_ID=dist-repo \
pnpm run publish:packages -- --only=@levin/admin-framework
```

业务模块发布示例：

```bash
NPM_REGISTRY=http://nexus.v-ma.com/repository/npm/ \
NPM_AUTH_FROM_MAVEN=true \
MAVEN_SERVER_ID=dist-repo \
pnpm run publish:admin-modules -- --only=@levin/oak-base-admin
```

安装依赖时通常使用 group 仓库，例如：

```text
http://nexus.v-ma.com/repository/npm-public/
```

发布同版本会失败。发版前应确认私服中已有版本，并在 `package-versions.json` 中配置新版本后同步。

发布前还应确认：

- `main`、`module`、`types` 和 `exports.default` 均指向 `dist`。
- `exports.development` 若指向 `src`，必须覆盖根入口和相关子路径，避免本地开发时根入口走源码、启动子路径走构建产物而形成两份运行时配置。
- `exports` 中没有 `./src/*` 这类绕过公共入口的源码深路径导出。
- 需要给第三方查看的源码和文档可以继续通过 `files` 随包携带。

## 11. 常见问题

### 编译或打包阶段看到 warning

本项目定位是前端公共模块集合，发布包主要面向 Vue/Vite 后台应用消费，不是纯 Node.js 运行库。第三方项目在编译或打包阶段可能看到一些来自公共模块、SFC、动态导入或样式处理的提示；只要最终构建命令退出码为 0，页面可打开，核心功能可用，这类提示通常不是致命问题。

常见非致命提示包括：

- `vue-sfc-transformer is not installed`：表示公共包构建时没有把所有 `.vue` SFC 完全转成普通 JS。当前包允许发布 `.vue` 文件，由最终应用的 Vite/Vue 插件处理。
- `dynamic import will not move module into another chunk`：表示同一个模块同时被静态导入和动态导入，影响的是分包优化，不代表模块不可用。
- 打包日志中出现较大的 chunk 或 CSS 文件：通常是通用后台框架、VXE Table、JSON 编辑器、表单组件等公共能力集中打包导致。需要优化首屏性能时再按实际页面拆分，不应先按日志大小盲目删除公共能力。

需要处理的阻断问题通常具备以下特征：

- 构建命令退出码非 0。
- Vite、Sass、TypeScript 或 Rollup 明确提示找不到文件、找不到导出、语法无法解析。
- 页面运行时出现白屏、路由打不开、核心 API 调用失败或控制台新增错误。
- 发布包的 `exports` 指向不存在的 `dist` 文件。

遇到提示时，建议先按顺序确认：最终构建是否成功、应用页面是否能打开、提示是否来自公共模块的非阻断构建策略。如果构建成功但提示影响第三方判断，可以把完整日志提交给公共模块维护方评估是否需要收敛日志或优化打包策略。

### 页面打开空白

检查是否启用了对应模块、后端菜单路径是否能匹配页面注册表、最终应用覆盖页面路径是否正确。

如果页面在打开弹窗、抽屉或快捷编辑入口后切换菜单出现内容区空白，优先升级到包含路由内容区稳定根节点和错误隔离的 `@levin/admin-framework` 版本。第三方宿主项目还应把公共包随带的检查命令接入自身 `check` 或 CI：

```bash
pnpm exec levin-check-route-transition .
```

该检查会阻止 `RouterView + Transition` 直接包裹 `KeepAlive` 或路由页面组件的危险写法。公共框架布局已经内置运行时兜底；如果第三方项目自定义了全局布局、二级布局或页签缓存容器，仍必须保持 `Transition` 的直接子节点是稳定单根 DOM 容器，再在容器内部渲染实际页面组件。

### 样式缺失或菜单页签异常

检查 Tailwind `content` 是否扫描了 `node_modules/@levin`、`@vben`、`@vben-core` 以及 pnpm `.pnpm` 下的传递依赖。

### 接口 404

检查代理是否覆盖对应后端模块前缀，基础模块为 `/com.levin.oak.base`。

### 图片或附件无法回显

检查 `/lfs` 等资源路径是否转发到后端。

### 图片或文件上传失败

先确认页面使用的是 `@levin/admin-framework/framework-commons/app/api/file-storage-service` 的公共上传封装，上传请求是否命中后端 `FileStorageController`。单文件上传应返回字符串 URL；如果返回对象或空值，公共封装无法稳定回写表单，应优先修正后端返回。

### 多模块页面冲突

确认每个模块的 `name`、路由 `name`、页面注册路径和后端菜单 `path` 都带有稳定模块语义，避免不同模块使用同一标识。

### 资源权限的共享勾选状态

资源权限分配以权限表达式作为唯一选择标识。同一权限无论出现在多少个 Tab、菜单、页面操作或重复元素中，都共享当前授权对象的一份勾选状态；在任意位置勾选或取消，其他位置同步变化。不同角色、授权对象及独立编辑窗口不会串联状态。

重复出现的权限项右上角显示纯数字小角标 N，数量包含当前位置；仅在 N 大于 1 时展示。悬停显示“N处共用权限”，点击数字角标可查看全部中文层级位置。同名的不同元素分别计数；搜索、折叠和切换 Tab 不会减少共享数量。这里统计的是当前授权窗口完整可选树中的位置，不是全系统用户数、角色数或打开的浏览器页面数。

取消共享权限后，页面提示其他位置已同步取消，并提供“查看同步取消的位置”入口。取消整个菜单、分组或 Tab 时，也会同步取消其中相同的权限；操作先修改待保存状态，点击保存后生效。

菜单自身的“展示”权限与其下操作权限分开处理：仅取消子操作时保留已经选中的菜单展示权限，但不会新增原本未选的菜单权限；取消整个菜单时才一并移除其自身及子树权限。存在覆盖目标的通配授权时，取消操作会解除该覆盖，并保留当前可选范围中其他已选权限。

保存只提交一次去重后的权限表达式列表，不按 Tab 分别保存，也不依靠“菜单最后保存”覆盖其他 Tab。组件接入方应将所有位置绑定到同一授权对象的 `value` / `update:value`，不要在保存时重新合并各 Tab 的旧选择。

### 操作权限与关联的资源权限

界面按钮统一称为“操作权限”，后端 API 对应权限统一称为“资源权限”。每项操作权限在菜单已保存的 `opButtonList` 中使用页面内唯一的 `opName`，并以 `requireAuthorizations` 数组显式保存零个或多个关联资源权限；不根据按钮名称或 API 地址推断关系，也不拼接通配表达式。操作没有关联资源权限时，仍可作为独立操作权限分配。

菜单管理的“页面操作”编辑器中，每项资源权限以标签展示，标签文字完全使用权限树返回的中文路径，例如“基础模块 / 团队 / 新增”；前端不补写或改造节点名称。资源权限树尚未加载时才回退显示原始表达式。悬停可查看完整表达式；点击标签的关闭按钮只移除该一项，“选择权限”可追加或调整多项，“清空”才移除全部。

操作权限使用点击图标，资源权限使用接口连接图标。关联的资源权限不在树中展开；操作权限右上角用红色数字角标显示关联数量（按表达式去重），鼠标悬停显示标题“关联的资源权限”，下方每行显示一个资源权限名称，长列表可以滚动查看。蓝色角标仍表示共用位置数，悬停显示“N处共用权限”，两类数量互不替代。

勾选操作权限时，同时选中其关联的资源权限，其他位置同步更新。操作自身表达式与全部关联资源权限均已授权时显示全选；仅部分资源已选时显示半选。直接取消一个资源权限不会被操作权限重新补回。

取消操作权限，或批量取消涉及操作权限时，先弹出“确认取消操作权限”，提示“将同时取消以下 N 个关联的资源权限：”并完整列出资源权限名称。批量操作合并去重列表，点击“返回”或关闭不改变勾选；点击“确认”后，操作权限及关联资源权限一起取消，其他共用位置同步变化，保存后生效。外部授权对象或数据变化时关闭过期确认，不应用旧的取消范围。
